# Provider-directory intake: an evidence-preserving local workflow

A clinic's changed roster often arrives in a different format from the directory it is supposed to correct. Importing rows is only the first problem: operators need to know what was received, what was interpreted, which operating location is involved, and whether an approved correction was actually observed afterward.

This implementation extends a tested Python/FastAPI/React/SQLite portfolio application with durable CSV/XLSX mapping and quarantine, explicit saved-JSON/public-source profiles, retained original bytes, stable scoped work, later observations, and accountable human review. A synthetic two-location clinic journey demonstrates acceptance, repeat delivery, approval, simulated submission, verification and failed-verification reopen. A first-time reviewer can load those synthetic inputs from the UI, review suggested columns, and explicitly accept valid rows without locating files. NPPES and Medicare clinician examples are separate reference scenarios, with synthetic saved responses clearly distinguished from bounded live reads.

The key engineering decisions are deliberately bounded: one local service and SQLite, digest-addressed artifact files, explicit adapters rather than a generic connector platform, transactionally consistent acceptance/events, and exact provider plus separate location relationships. Reordering a file does not create new scoped work. A corrected later observation attaches evidence without silently verifying the operator's case. Stale browser versions conflict and retain drafts.

A read-only XLSX handoff carries all durable cases or one selected case, current ownership/follow-up, scoped initial/later observations and append-only decisions from one SQLite snapshot. Listed, requested, approved and observed values remain distinct. Text-safe identifiers and chunked complete payloads prevent Excel coercion, formula execution and silent cell truncation. UI filters do not narrow the all-work export.

Qualification includes null/identifier regressions, migration preservation/rollback, restart and mid-acceptance failure, error-envelope retention, native source grain, HTTP integration, and browser journeys at desktop/phone widths. The [baseline evidence index](evidence/intake_2_0/README.md) and [dated follow-up](evidence/employer_readiness/README.md) record exact commands/results, screenshots, live-read scope and measured import limits. The [offline demonstration](operations_governance/sop_provider_remediation.md) can be reproduced without accounts or network after dependency installation.

For an interview, begin with the row at `Clinic roster!5` that stays quarantined, then show ZIP `02108`, separate NORTH/SOUTH identities, repeated receipt without duplicate work, accountable approval/observed verification, a case XLSX with row locators and history, and restart with the same retained root. Explain three failure cases: why a repeated file needs a new receipt but no duplicated cases; why one NPI cannot select a practice phone; and why an append-only history still needs an expected-version check. Walk through the source locator and immutable snapshot before showing the active proposal and observed result. Be explicit that submission/verification are asserted synthetic operations and that public sources do not certify directory truth.

The transferable engineering example is the record lifecycle: an external file becomes retained evidence, interpreted rows, relationally linked observations, review work and a reproducible handoff. A technical review can inspect Python parsing/validation, SQL joins and transactions, identifier/provenance design, controlled state changes, repeat-delivery safety and recovery. SQLite is the current local engine. The planned operational SQL pack and recurring-file improvements make these capabilities more visible without changing the healthcare use case.

This is a local portfolio system. It does not implement authentication, hosting, payer writes, automatic entity merging, national replication or clinical/credential certification. Larger work queues, asynchronous job progress and evaluated identity suggestions are future work triggered by measured operational need.
